# LED 遅延（ジッタ）計測 結果分析

計測スケッチ: `LED_delay_measure.pde`（Processing、BPM 同期 LED の点灯タイミングを CSV 記録）
データ: `jitter_log_*.csv` 24 ファイル（2026-07-07 〜 2026-07-08、有効 17 ファイル・計 **1,544 拍**）

jitter_ms = 実際の点灯時刻 − 期待点灯時刻（正 = 遅れ、負 = 早い）

## 1. 全体サマリー

| 指標 | 値 |
|---|---|
| サンプル数 | 1,544 拍 |
| 平均 | **+7.6 ms**（常に遅れ方向） |
| 標準偏差 | 3.1 ms |
| 最小 / 最大 | 0 ms / +20 ms |
| p95（絶対値） | 12 ms |

**負のジッタ（早く点灯）は 1 件もない**。ズレは 0〜20 ms の範囲に収まり、
大半（約 70%）が 6〜10 ms に集中している。

## 4. 原因の考察: 60fps フレーム量子化

LED の点灯判定は Processing の `draw()` 内で行っており、`draw()` は 60fps
（フレーム周期 16.7 ms）でしか回らない。そのため期待時刻を過ぎても、
次のフレームが来るまで点灯できず、**ズレは常に遅れ方向・最大約 1 フレーム分**になる。

さらに、点灯時刻はフレーム境界に量子化されるため、次の期待時刻
（= 実点灯時刻 + 拍間隔）とフレーム境界の位相差は毎拍ほぼ一定になり、
**平均ジッタは「(−拍間隔) mod 16.7 ms」で予測できる**。実測との比較:

| BPM | 拍間隔 | 理論ジッタ | 実測平均 | 差 |
|---:|---:|---:|---:|---:|
| 40 | 1500 ms | 0.0 ms | +2.5 ms | +2.5 |
| 53 | 1132 ms | 1.3 ms | +3.4 ms | +2.1 |
| 60 | 1000 ms | 0.0 ms | +4.0 ms | +4.0 |
| 66 | 909 ms | 7.7 ms | +8.6 ms | +0.9 |
| 79 | 759 ms | 7.7 ms | +8.2 ms | +0.5 |
| 80 | 750 ms | 0.0 ms | +1.5 ms | +1.5 |
| 100 | 600 ms | 0.0 ms | +1.6 ms | +1.6 |
| 103 | 582 ms | 1.3 ms | +2.0 ms | +0.7 |

全 BPM で理論値 +1〜4 ms に収まっており、量子化仮説と整合する
（残差の +1〜4 ms はフレーム周期の揺らぎと描画処理の遅延分）。
つまり **観測されたジッタの支配要因は BPM 検出やシリアル通信ではなく、
描画ループの時間分解能**である。

## 5. テンポへの影響: ジッタは毎拍累積する（累積ドリフト）

`actual_ms` の隣接差分から**実際の拍間隔**を求めると、理想値より系統的に長い:

| BPM | 理想間隔 | 実測平均 | 誤差/拍 | フレーム換算 |
|---:|---:|---:|---:|---|
| 53 | 1132.1 ms | 1134.3 ms | +2.3 ms | 68 フレーム = 1133.3 ms |
| 66 | 909.1 ms | 916.7〜918.5 ms | **+7.6〜+9.4 ms** | 55 フレーム = 916.7 ms |
| 79 | 759.5 ms | 767.8 ms | +8.3 ms | 46 フレーム = 766.7 ms |

実測間隔は「理想間隔を超える最小のフレーム数 × 16.7 ms」に**切り上げ量子化**
されており、理論とよく一致する。

実 LED は `prevMillis = now`（実点灯時刻基準）で更新するドリフト型のため、
この超過分は毎拍リセットされず**累積する**。帰結として:

- 記録している jitter_ms は「1 拍ごとの間隔の超過分」であり、
  **平均ジッタ +7.6 ms/拍 = そのまま累積遅れの速度**になる
- BPM 66 では実効テンポが約 65.4 BPM（0.8% 遅い）となり、
  理想タイミングから **1 分あたり約 0.5 秒遅れていく**
- 一方、基準 LED は `refPrevMillis += interval`（理想時刻基準）で累積しない。
  画面上で 2 つの LED が徐々にずれて見えるのは、この設計差そのもの

なお、セッション内でのジッタは非常に安定している（293 拍のセッションで
前半平均 +9.3 ms / 後半平均 +9.7 ms、隣接拍の変化 std 2〜3 ms）。
時間経過や負荷による劣化は見られない。

## 6. 結論

- **1 拍単位のズレ**は最大でも 20 ms、95% は 12 ms 以内。音楽と光の同期ズレとして
  人間が知覚できる閾値（一般に 20〜30 ms）を下回っており、単発では気づけない。
- ただしドリフト型更新のため**ズレは毎拍累積し、BPM 66 では 1 分で約 0.5 秒遅れる**。
  数十秒以上音楽と並走させる用途では、こちらが実質的な問題になる。
- 原因はいずれも 60fps の描画ループによる量子化で、システム固有の遅延や
  BPM 検出精度の問題ではない。

### 改善するなら

1. **実 LED も理想時刻基準で更新する**（`prevMillis = now` をやめ、基準 LED と同じ
   `prevMillis += interval` にする）— 累積ドリフトが消え、残るのは ±1 フレームの
   単発ジッタのみ。累積問題への根本対策。
2. `setup()` で `frameRate(240);` を指定する — 時間分解能が 16.7 ms → 約 4 ms に
   なり、単発ジッタ・累積速度とも約 1/4 になる。変更 1 行で最も手軽。
3. LED 判定を `draw()` から独立したスレッド（`Thread` + `millis()` 監視）に
   移す — フレームレート非依存で 1 ms 精度が狙えるが、実装コストが上がる。

なお Arduino 実機では `loop()` が数十 µs 周期で回るためこの量子化は起きない。
本現象は **Processing 移植版（60fps の draw() 内で時刻判定する構造）に固有**であり、
実機の LED 遅延を見積もる際はこの分を差し引いて評価する必要がある。
